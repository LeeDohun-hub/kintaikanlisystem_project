# 근태관리 시스템 — 설계 회의 자료 (초안)

> **용도:** 내일 이후 **데이터베이스 설계**·**애플리케이션 설계** 단계로 넘어가기 위한 공통 이해와 논의 포인트 정리.  
> **전제:** 현재 저장소의 구현은 **예습·프로토타입**이며, 본 설계에서 확정·변경될 수 있음.

---

## 1. 회의 목표 (제안)

| 단계 | 목표 |
|------|------|
| **DB 설계** | 엔티티·관계·제약·인덱스·마이그레이션 전략 합의 |
| **앱 설계** | 레이어 구조, API 명세, 인증·권한, 화면–API 매핑, 비기능 요구 합의 |

---

## 2. 요건 범위 요약 (교육용 요건 정의서 기준)

- **직원:** 근무 입력(일자·시간·휴식·구분·코멘트·프로젝트), 본인 근무 이력 조회  
- **관리자:** 전체 근무 조회, 통계/집계, 매출·손익(단가·월별), 캐시플로우(입금 예정)  
- **기술 스택(안):** 백엔드 Java/Spring Boot, 프론트 React, DB MySQL, REST(JSON), 인증은 세션 기반(향후 JWT 등 검토 가능)

---

## 3. 예습 프로젝트에서 이미 다뤄 본 것 (토대)

### 3.1 시스템 구성 (현재 저장소 기준)

```
[브라우저] React(Vite) :5173  →  proxy  →  Spring Boot :8080  →  MySQL :3306 (kintai_db)
```

- **프론트:** 라우팅, 로그인/회원가입, 직원·관리자 메뉴 분리, Axios + `withCredentials`  
- **백엔드:** 세션 로그인, 인터셉터로 `/api/**` 보호(인증 예외 경로 별도)  
- **DB:** `sql/schema.sql`에 테이블 초안(직원·프로젝트·근태·단가·입금 예정)

### 3.2 논리 데이터 (스키마 초안 요약)

| 테이블 | 역할 |
|--------|------|
| `employees` | 직원 코드, 이름, 비밀번호(BCrypt), 역할(ADMIN/EMPLOYEE) |
| `projects` | 프로젝트 코드·이름 |
| `attendance` | 직원별 근무일·시간·휴식·구분·코멘트·프로젝트 FK |
| `unit_prices` | 직원·월(YYYY-MM)별 단가 |
| `payment_schedules` | 입금 예정일·금액·상태 등 |

→ **설계 회의에서 할 일:** 컬럼 추가/삭제, 정규화 수준, 이력 테이블 필요 여부, 감사(audit) 컬럼, 소프트 삭제 여부 등 **재검토**.

### 3.3 화면–역할 (프론트 라우트)

| 경로 | 역할 |
|------|------|
| `/login`, `/register` | 공개 |
| `/work-input`, `/work-history` | 직원 |
| `/dashboard`, `/work-view`, `/statistics`, `/revenue`, `/cashflow` | 관리자 |

### 3.4 백엔드 API 현황 (참고)

- **구현·확인된 중심:** `POST/GET /api/auth/*` (로그인·로그아웃·me·회원가입)  
- **프론트가 호출하도록 작성된 호출:** `/api/projects`, `/api/attendance`, `/api/employees`, `/api/statistics/...`, `/api/unit-prices`, `/api/payment-schedules` 등  
→ **본 설계에서** REST 리소스 설계·컨트롤러 분리·DTO·검증 규칙을 **문서로 확정**할 것을 권장.

## 4. 데이터베이스 설계 회의 안건 (제안)

1. **엔티티 목록 확정**  
   - 예습 스키마를 채택할지, 테이블 분할/통합할지 (예: 근태와 프로젝트 할당, 휴가/결근 구분).  
2. **관계·제약**  
   - FK, ON DELETE 정책, `employee_code` vs 내부 `id` 사용 범위.  
3. **인덱스**  
   - 월별 조회·직원별 조회 패턴에 맞는 복합 인덱스.  
4. **코드/상태값**  
   - `work_type`, `payment_schedules.status` 등 ENUM vs 코드 테이블 vs VARCHAR.  
5. **시드·마이그레이션**  
   - `schema.sql` 단발 vs Flyway/Liquibase 도입 여부.  
6. **보안**  
   - 비밀번호 해시만 저장, 개인정보·마스킹 정책(관리자 화면).

---

## 5. 애플리케이션 설계 회의 안건 (제안)

1. **아키텍처**  
   - 레이어(controller / service / repository), 트랜잭션 경계, 예외 처리 공통화.  
2. **인증·인가**  
   - 세션 유지 방식, 역할(ROLE) 모델, API별 권한 매트릭스.  
3. **API 설계**  
   - URL 규칙, 페이징·필터(월별·직원별), 에러 응답 형식(JSON).  
4. **프론트**  
   - 상태 관리 범위, API 클라이언트(axios 인터셉터·401 처리 정책).  
5. **비기능**  
   - 동시 접속·세션 타임아웃, 로깅, 배포 구조(정적 파일 + API 서버).
